Case Study

CoffeeSpy

A crowdsourced coffee price tracker for Wellington cafes, modelled on the petrol price app Gaspy. Users report what a coffee costs at a cafe, and other users confirm or dispute the report.

Type
Solo project, built to learn API design and mobile development
Client
Flutter (Dart), targeting Android and iOS
Server
Elixir / Phoenix, JSON API only
Data
PostgreSQL through Ecto, run in Docker
Auth
JWT (Guardian), passwords hashed with PBKDF2
Source
GitHub Link

Architecture

The client and server are separate applications that share nothing but the API contract. The Phoenix application exposes JSON endpoints and holds all the business rules; the Flutter client holds the presentation state only. 

Flutter client                       Phoenix API                 PostgreSQL
  AuthService  ── POST /api/login ─▶  AuthController   ── Ecto ──▶  users
  ApiService   ── GET  /api/... ───▶  PriceReport      ── Ecto ──▶  cafes
               ◀── { "data": ... } ──  controllers                  price_reports
  (JWT in secure storage, sent as a Bearer header)                  confirmations

Table names indicative

What it does

  • Registration and Login, issuing a signed token the client stores in the platform's secure storage
  • A multi-step form for submitting a price report against a cafe
  • Confirmation of other users' reports, so a price gains credibility as more people corroborate it
  • A profile screen listing the user's own reports, with a guest state for users who are not signed in
  • Light and Dark themes, implemented with a custom Flutter ThemeExtension

Decisions

Business rules are enforced on the server

A user should not be able to confirm their own report. Hiding the button in the app is not sufficient, because anyone holding a valid token can call the API directly. The check is made in the server before a confirmation is sent to the database; the client's job is only to avoid offering an action that will be refused.

Stateless Tokens

Tokens are signed JWTs with no server-side session table. This keeps the server simple and horizontally scalable. The cost is that a token cannot be revoked before it expires; for an app of this sensitivity that is acceptable, but it would not be for one handling personal records.

Shaping responses for the client

The profile screen lists reports alongside the cafe each was made at. Returning only a cafe ID would force the client to make one further request per report, which would cause delays when scaled. The server instead includes the cafe name in the report payload, so the screen loads with a single request.

PBKDF2 over bcrypt

The usual Elixir bcrypt library depends on a native C extension, which proved unreliable to compile on my Windows development machine. pbkdf2_elixir is implemented in Elixir and is an accepted password-hashing function, so I used it instead.

Separating authentication from data access in the client

Token handling lives in an AuthService; requests for application data go through an ApiService. Screens depend on these services rather than making HTTP calls themselves, so the network layer can be changed or mocked in one place.

Problems and how I diagnosed them

The app could not reach the server from a phone

Requests worked in the emulator and failed on a physical device. On the phone, localhost refers to the phone itself, so the client was configured with the development machine's LAN address instead. Android then rejected the requests because it blocks unencrypted HTTP by default; I allowed cleartext traffic in a development-only network configuration rather than across the app.

Responses parsed as empty

Phoenix's generated JSON views wrap every payload in a data envelope. The client was decoding the top-level object as the resource. The fix was to unwrap data in one place in ApiService rather than in each screen.

Migrations ran in the wrong order

After I renamed a migration file by hand, Ecto ran it before a migration it depended on, because order is taken from the timestamp in the filename. I restored generator-assigned timestamps rather than editing them.

Two latent bugs found during review

While building the profile screen I found a context function being called without its required user_id argument, and a preload of :cafes on a schema that declares belongs_to :cafe. Neither path had been exercised yet, which is the case for tests.

What I would change

  • Add ExUnit tests for the confirmation rules and controller responses before adding features.
  • Short-lived access tokens with refresh tokens, so a compromised token stops working without a server-side session table for every request.
  • Complete the deferred password-reset flow and settings screen.
