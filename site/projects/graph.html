Case Study

Graph Visualiser

A Java desktop application that generates random connected weighted graphs and uses two pathfinding algorithms to locate the shortest path. This project was written to understand how the two algorithms differ, and Maven was added later to accommodate the unit tests using the JUnit suite which found two bugs in how the connections formed.

Type
Personal project
Language
Java 25, Swing for the interface
Build
Maven, JUnit 5
Source

Generating a connected graph

A randomly generated graph is only useful for pathfinding if every node can be reached. Rather than generating edges at random and checking connectivity afterwards, the generator builds the graph one node at a time so that it is connected at every step:

  1. Each new node is joined to a randomly chosen node already in the graph. This forced connection guarantees that the graph stays connected.
  2. The new node is then offered a connection to every other node in the graph. The chance of each connection starts at 90% and falls by 10 percentage points for every connection the two nodes already have, to a minimum of 10%. This spreads connections across the graph instead of letting a few nodes become hubs.
  3. A final pass gives any node with fewer than two connections another one to another random node, so that there is usually more than one route between two nodes and the algorithms have a choice to make.

Pathfinding

Dijkstra's algorithm

Dijkstra's algorithm expands nodes in order of their distance from the start, using a priority queue, and records each node's predecessor so the path can be rebuilt once the destination is reached. It always finds the cheapest path, but explores in every direction.

A* search

A* orders the queue by distance travelled plus an estimate of the distance remaining, using the straight-line distance between nodes as the estimate. This steers the search towards the destination and explores fewer nodes. It only finds the cheapest path if the estimate never exceeds the real remaining cost, which turned out to matter.

Making it testable

The project had no tests and could not easily be given any. Two changes made that possible:

  • The pathfinding code lived inside the Swing window class, so testing it meant creating a window. I moved both algorithms into a separate Pathfinder class that takes a list of nodes and knows nothing about the interface.
  • Generation used its own sources of randomness, including SecureRandom for values that fed into the hash codes used to seed later steps, so no two runs produced the same graph. The generator now takes a Random as a constructor argument. Passing a seeded instance gives the same graph every time, so a failing test can be reproduced exactly.

Tests

There are two kinds of test. The first builds small graphs by hand where the correct answer is known, such as a route of several cheap edges that should be preferred over one expensive direct edge, a path from a node to itself, and a node that cannot be reached. Each of these is a parameterised test that runs against both algorithms, so the results show Dijkstra and A* side by side.

The second kind checks a property over many generated graphs: for 200 seeded graphs, A* must find a path of the same total cost as Dijkstra. Hand-written examples only cover the cases I thought of; this test covers cases I did not. This test will fail occasionally, and this is due to my relative inexperience with the pathfinding algorithms to diagnose the issue.

What the tests found

The same connection had two different weights

Each connection is stored once in each direction, and each direction was given its own random weight. Travelling from A to B could therefore cost a different amount from travelling B to A, and the label drawn on the edge showed only one of the two. Every generated graph was affected. The fix was to choose one weight per pair of nodes and use it for both directions.

What I would change

  • Run the tests in GitHub Actions on every push, as my other projects do.
  • Move the test classes into the same package as the code they test.
  • Reject invalid node ids with a clear error. A negative start id currently causes an ArrayIndexOutOfBoundsException inside the algorithm.
  • Count the nodes each algorithm explores and show it in the interface, to make the difference between them visible.
