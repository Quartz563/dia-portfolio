Ironfolk Combat Inc Website

The public website for Ironfolk Combat Inc, a Historic European Martial Arts (HEMA) club in Wellington. I built and maintain it, including hosting, domain configuration and security updates. It is one of the projects in active production and has real users depending on it.

Requirements

The club had attempted three times in the past to create a website that would advertise the club, it's rules, training locations and general fees. In the past, these attempts would often use website makers, but would not provide the customisability that the club needed. As someone experienced with general development in the Phoenix framework, I offered to try my hand.

The general requirements for the website were the following:

  • Show off the club in a positive light
  • Allow for people to sign up to the club and review the rules and training times
  • Allow for messages and alerts to be posted to the main page of the website
As this was a volunteer project; no budget was allocated, and I was requested to present it at the AGM for 2025.

Problems and how I diagnosed them

The site was reachable at two addresses

The site answered on both www. and the bare domain, serving identical content from two URLs. This split the search ranking between them and made the links inconsistent. Rather than relying on DNS alone, I wrote a small Phoenix plug, CanonicalRedirect, placed in the endpoint before the router. It inspects the request host and, if it is not the canonical one, responds with a 301 permanent redirect to the same path on the canonical host. 


defmodule IronfolkCombatWeb.Plugs.CanonicalRedirect do
  import Plug.Conn

  def init(opts), do: opts

  def call(%Plug.Conn{host: "www.ironfolkcombat.co.nz"} = conn, _opts) do
    conn
    |> put_resp_header("location", "https://ironfolkcombat.co.nz#{conn.request_path}")
    |> send_resp(301, "")
    |> halt()
  end

  def call(conn, _opts), do: conn
end

Paying for infrastructure nothing used

Reviewing the Fly.io account, I found a second PostgreSQL cluster that was a duplicate of the main that the application was not connected to. I confirmed nothing referenced the second cluster before removing it, which reduced the running cost and number of services exposed.
